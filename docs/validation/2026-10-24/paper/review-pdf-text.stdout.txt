Credentials reach output through utterly ordinary debugging. An agent asked to fix a failing integration test may
run printenv to check configuration, cat .env to inspect
it, curl -v to reproduce an HTTP error (which echoes the
Authorization header), or simply rerun a test whose failure
message embeds the database URL. Each of these discloses a
secret the human never intended to share, and because transcripts cannot be retracted from a provider’s logs, the only
safe response is rotation. Practitioners report this happening repeatedly in normal use [14, 56], and a study of 17,022
agent skills reports debug-output exposure in 1,007 of 1,371
vulnerability issues (73.5%), where agent frameworks feed
output into model context [16]. This percentage describes
that study’s issue category, not a population-wide rate of
agent credential leakage. Once a value has entered context it
also resurfaces in places transcript scrubbing cannot reach,
such as reasoning traces [59].
Existing tools each cover part of the problem. Secret
managers’ run wrappers inject values into a child’s environment [2, 24, 41]; 1Password’s also conceals values in the
child’s output, but none of them mediates which commands
an agent may run with which secrets. Per-tool file restrictions
alone can leave indirect read paths [25, 53]; host-enforced
filesystem controls can protect those paths as well [6, 7].
Credential brokers control authentication [1, 12]; filtering
subsequent command output requires an output boundary.
Proxy-substitution designs keep real values out of client
processes. HTTP-specific proxies operate on traffic routed
through their supported HTTP(S) paths [7, 26, 40]; protocolaware brokers also support database and SSH connectors [20].
CI runners have long masked known secrets and their encodings in job logs [31, 32], and agent-side tools also inject
secrets and scrub tool output by literal matching [27, 61];
Prismor additionally documents command policy and human approval [62, 63]. Our focus is the specific combination
of transformation-aware streaming known-value redaction,
session-bound authorization, and OS containment, evaluated
at the agent’s tool boundary for command-line programs.

LLM coding agents run shell commands, and their output
becomes model context. A credential printed by a debugging
command can therefore reach the model provider and local
transcripts. We present ironrun, an open-source runtime
that injects secret values into child processes as environment variables or temporary files and filters known values
and supported encodings before output reaches the agent.
It combines value-blind Model Context Protocol interfaces,
session-bound human authorization, a streaming redactor
with whitespace-tolerant, fragment, and alignment-aware
matching, and platform-specific OS controls with a hashchained audit log. We state a chunking-invariance property
for fixed patterns, bounded matching spans, successful writes,
and a final flush, and present current regression case studies
for approval integrity, agent-reachable surfaces, encoding
structure, and non-vacuous containment tests. In a paired
reproduction using the same checked harness on v0.5.0 and
the reviewed runtime, 52 of 126 transformation/credential
cases permit at least 50% case-insensitive contiguous recovery on the baseline, versus 28 on the reviewed runtime. For
ordinary-tool transformations the counts are 21 of 72 versus
3 of 72; the three remaining cases involve a 12-byte password below fragment protection. A fresh current-only run
reproduces these current counts. Shared-host Linux diagnostics additionally expose structured-value over-redaction
and measure throughput and median spawn costs; they do
not establish deployment leak rates, tail latency, or usability.
Known-value redaction reduces accidental disclosure, but
thresholds, partial disclosure, and unregistered transformations limit coverage. Authorization, protected executable
code and inputs, and isolation must bound deliberate exfiltration.

Introduction

Coding agents such as Claude Code, Codex, and Cursor operate by issuing tool calls—most importantly, shell commands—
and reading their output. That output is appended to the
model’s context window, transmitted to the model provider
on every subsequent turn, and typically persisted by the agent
host as a local transcript (Claude Code, for example, stores
JSONL session logs under ~/.claude/projects/). Anything

Threat Model

Adversaries. We distinguish three:
A1 Accidental disclosure. An honest agent runs ordinary
commands that happen to print secrets. This is the common case and the primary target.
A2 Manipulated agent. A prompt-injected or misaligned
agent [33] tries to move a secret into its context or off the
machine, but acts only through its tools: MCP calls, its
native shell, and file edits.
A3 Hostile same-user code. Arbitrary native code running
as the operator’s UID. It can read the user’s keychain,
attach to processes where the OS permits, and rewrite
user-owned files. A3 is out of scope; containing it requires
a separate OS user, container, or VM.
Goals.
G1 Value-blind interfaces. Agent tools expose no plaintext
secret-value or vault-key fields. Trusted local input and
explicit CI mask emission use separate operator channels
(Section 4.1).
G2 Output filtering. The output boundary replaces recognized literal and derived matches under the defined matching policy; thresholds, overlaps, and transformations limit
confidentiality.
G3 Least authority. Saved commands restrict argv and secret selection. Optional leases and trusted-workspace
grants bind authority to a session, environment, and expiry; revocation is checked on the next call.
G4 Containment. Requested network isolation and processgroup time limits apply on supported platforms. Linux
additionally provides syscall filtering and a core-dump
limit; macOS does not implement those Linux-specific
controls.
G5 Accountability. With auditing enabled, successful appends retain command metadata and secret names in a
hash chain. Availability and integrity limits are explicit in
Section 4.6.

Background

Agent tool loops. An agent host repeatedly sends the conversation to a model, receives tool calls, executes them locally,
and appends results. The Model Context Protocol (MCP) [52]
standardizes how a host discovers and invokes local tool
servers over stdio. Every byte a tool returns becomes model
input, is retained for the rest of the session, and is commonly
written to disk by the host.
Why output is the hard channel. Secrets can leave
through three channels: inputs the agent writes (a value
typed into a command line), outputs a command prints, and
side effects (network, files). The first is solvable by never giving the agent the value; the third is the domain of sandboxes.
The second is the subtle one: an agent that has never seen a
credential can still cause it to be printed, merely by running
the program that uses it. Rotation is the only remedy after
the fact.

Non-goals. ironrun does not attempt to stop an authorized
process that deliberately transforms a secret with an arbitrary
function before printing it (Observation 1); does not defend
against A3; does not remove data from provider logs; and
does not guarantee physical erasure of temporary file secrets
on SSDs or copy-on-write filesystems.

Scenarios. Three representative accidents motivate the
design: (1) a connection failure prints a DSN with an
embedded password; (2) curl -v -u deploy:$TOKEN
prints Authorization: Basic followed by the base64 of
deploy:<token>; (3) docker compose config prints the interpolated environment. In (2) the token never appears literally—
it appears base64-encoded at a byte offset that depends on the
username, a case that matters in Section 7.

A note on A2 and the native shell. Agent hosts typically give the agent its own unrestricted shell in addition to

4.3

Resolution and storage

Secrets come either from an existing manager through its
CLI (1Password, HashiCorp Vault, Doppler, Infisical), from
an owner-only env file outside the repository, or from ironrun’s own encrypted vault (Fig. 3). The vault keeps a random
32-byte root key in the OS credential manager. Each environment (a scope) is sealed under a fresh 32-byte data key on
every write; the data key is wrapped by the root key with
AES-256-GCM, and both encryptions bind version, purpose,
project, and scope in their authenticated data, so ciphertexts
cannot be moved between environments or projects. The
whole manifest carries an HMAC-SHA256 under the root key
and is committed by write-temp, fsync, rename, and directory fsync. Only names, kinds, and timestamps are stored
unencrypted, under .ironrun/ in the project.
File secrets (e.g. a service-account JSON) are materialized
only for the duration of a run, in a fresh 0700 directory outside the repository, with O_EXCL 0600 files and validated basenames; only the path is injected, and the contents are registered for redaction.

Authorization mechanisms

ironrun combines four authorization mechanisms:
1. Strict commands. The policy file lists exact argv vectors
and the secrets each receives. The agent calls run_sealed
with a command ID; no shell expansion is performed by
the wrapper, and argv[0] may not be a shell. The policy is
re-read on every call.
2. Leases. With require_agent_leases, a strict command
also needs an unexpired, unrevoked lease bound to the
MCP session, environment, and command set (default 1 h,
maximum 24 h).
3. Trusted workspace sessions. For everyday development, the operator grants one MCP session arbitraryargv execution against one project environment for a
bounded time (default 2 h). staging and prod require separate grants.

4.4

Matching tiers. At each buffer position the writer tries, in
order:
1. Exact, longest pattern first, using a first-byte index.
2. Gap-tolerant: the pattern’s bytes appear in order with
interleaved whitespace or control bytes (≤ 0x20, 0x7F),
which covers terminal line wrapping, \r \n injection,
UTF-16LE null interleaving, and one-character-per-line
output. The consumed span is capped at the global span
𝑚 defined below.
3. Fragment: for patterns with 24 to 65,536 non-gap bytes,
every 12-byte window of the pattern’s gap-free projection
is indexed. Twelve output bytes that match a window, in
order and with any gap bytes between them, are extended
forward over the rest of the pattern and redacted. This
catches truncated and partial prints (one line of a PEM
key) and line-oriented dumps (xxd, od -c) whose offset
columns cut a value into per-line pieces.

4.5

Containment

The following controls reduce selected side effects. Requested
network isolation and the Linux child shim refuse execution
when their setup fails; their scope does not include filesystem
or general interprocess isolation.
• Network. Secret-bearing commands get no network
unless the policy opts out. On Linux ironrun enters fresh user and network namespaces [46, 47]
(CLONE_NEWUSER|CLONE_NEWNET with an identity UID/GID
map, so no privilege is needed); on macOS it wraps the
child in a Seatbelt [13] profile that denies only network*,
invoking /usr/bin/sandbox-exec [8] by absolute path.
Unsupported platforms refuse to run.
• Syscalls. On Linux the child is started through a reexec shim that sets NO_NEW_PRIVS, installs a seccompBPF filter [70] that checks the architecture, rejects the
x32 ABI, and returns EPERM for ptrace, process_vm_readv,
process_vm_writev, kcmp, perf_event_open, bpf, and
userfaultfd, then sets RLIMIT_CORE=0 and execs the target
in place.
• Lifetime. The child runs in its own process group; on
timeout, cancellation, or a signal to ironrun, the whole
group is killed, and any group member left after the child
exits is killed too. Descendants that detach with setsid
can escape this group and retain injected values; this is not
whole-process-tree containment. Temporary file secrets
are removed during normal error, cancellation, timeout,
and success cleanup, with stale-directory recovery after
crashes.

4.6

Lesson 1: human review depends on the enforced
artifact. The approval regression tests insert proposalcontrolled newlines, Unicode line separators, carriage returns,
and YAML-shaped text into reasons, references, names, and
argv. They parse the resulting policy and reject any added
command beyond the intended proposal. A separate check
changes proposal contents after computing the review digest
and requires approval to fail without changing the policy or
consuming the replacement. These checks exercise serialization and content binding; they do not measure whether
developers understand the approval interface. The general
rule is that human approval must be bound to the parsed
artifact that will be enforced, with unambiguous argv boundaries.
Lesson 2: value-blindness must cover every reachable
surface. A CLI regression asserts that ironrun env share
does not resolve to a command. The CI mask regression
uses a synthetic multi-line value and requires each output
line to be a mask command, with each secret line separately
registered. These checks cover CLI reachability and a lineoriented protocol where printing a multi-line value as one
command would expose later lines. An MCP-only interface
review would not cover these surfaces.

Audit

When auditing is enabled and the child starts, the runner
attempts to append a JSONL record: command, argv scrubbed
for registered literal and encoded values, secret names and
kinds, redaction count, exit status, and sandbox outcome.
Each record hashes the previous record’s hash. Opening
the logger verifies the existing chain and refuses detected
corruption; a long-lived server does not replay it before every
run. Later append or sync errors warn without failing the
command, and policy can disable auditing. ironrun audit
verify detects inconsistent edits or ordering when hashes
have not been recomputed. This unkeyed chain does not
provide the authenticated or forward-secure history of secure
logging constructions [68]. Without a protected external
anchor [19], an attacker can rewrite and rehash the whole
file or truncate its tail (Section 8).

Lesson 3: encodings have structure. The redaction
shape tests exercise Basic-auth base64 with varying prefixes and byte alignments, JSON/percent escaping, hexdump
columns, and partial file-secret output. They complement
encoding enumeration with the formatting conventions of
specific tools. The paired leakage experiment in Section 7
supplies baseline/current evidence for that corpus; these current regression checks do not independently reconstruct the
history of each change.

Implementation
Lesson 4: a denied operation must actually be attempted. The network regression requires a distinct
DIAL_BLOCKED marker as well as nonzero exit, so a process
that fails before dialing does not count as successful isolation. A macOS-specific check separately requires a sandboxed fork/exec to return child-ok. Checks may skip when
the platform or isolation capability is unavailable; a skip is
not positive containment evidence. The Linux diagnostics
below do not validate the macOS-only path.

ironrun is implemented in Go, with unit tests, differential
tests, and redactor fuzzing. Release binaries are built with
CGO_ENABLED=0. The MCP server uses mcp-go. Platforms
are macOS and Linux on amd64 and arm64; Windows is
unsupported because its secret-entry paths would require
plaintext console input. Builds use -trimpath, commit-date
timestamps, and pinned modules. Releases carry SHA-256
checksums, an SBOM, and keyless Sigstore bundles [57]. The
installer and GitHub Action verify checksums and bundles;
npm verifies archive and binary hashes against its bundled
manifest, without independent Sigstore verification. CI runs
OpenSSF Scorecard, govulncheck, and scheduled fuzzing.

Observation 1. Known-value matching alone does not guarantee confidentiality against arbitrary transformations. An
authorized process can disclose a secret through an invertible
representation if the emitted representation avoids every registered match. Being unregistered is not sufficient: a transformation can still produce a registered pattern (for example, reversal
of a palindrome).
Redaction is therefore a defense against A1, not against an
A2 that can choose the program. Against A2, ironrun relies
on strict commands with host-enforced protection of executable code and inputs. Network isolation reduces network
egress but does not isolate writable files or local IPC; those
channels require additional host controls. The warn-only
entropy scan flagged 21 of the 28 threshold leaks, with warnings on 6 of the 98 cases below that threshold. The latter
need not be false alarms: partial or component recovery can
remain security-relevant below 50%. The gzip/base64 case
is instructive: the emitted representation looks unlike the
credential but is readily decoded, which is why it is included.

Method (RQ1). We generate six synthetic credentials
shaped like real formats: a Stripe-style key (32 B), a GitHub
PAT (40 B), an AWS-style secret (40 B), a Postgres URL with

uses. We then attack the agent-visible output with a decoder battery: identity, gap stripping, case folding, reversal,
ROT13, base64 and hex decoding at every alignment (with

leaks if at least 50% of the secret matches. This measures caseinsensitive contiguous disclosure, not necessarily a usable
credential. A shorter recovered component can still expose
the entire password inside a structured URL. Rates describe
this deterministic corpus, not a real-world probability of leakage.

Discussion and Limitations

Substitution avoids value exposure. A child that receives only a placeholder cannot print a credential it never
held. HTTP-specific proxies substitute values on supported
outbound HTTP(S) paths [7, 40, 58]; protocol-aware brokers
also support database and SSH connections [20]. Where a
broker supports the workflow, keeping values out of the child
is preferable. Local signing, direct file consumers, and unsupported connectors can still require credentials in the process;
output filtering addresses that remaining boundary and can
compose with brokers.

Redaction is a safety net, not a sandbox. Observation 1

State integrity against A2. Authorization state
(.ironrun/, ironrun.yml) lives in the project, where an agent
with file-edit tools can write it, and a trusted session can run
ironrun itself to change access. Same-user storage cannot
protect itself from same-user code. The principled remedy is
to move approvals and state behind a broker running as a
different user, with the agent host’s own file and command
restrictions guarding the checkout in the meantime.
Credential-store reachability. Keychain items created
through /usr/bin/security are readable by any same-user
process that invokes it, and the legacy file store keeps its
key beside its ciphertext. Both are consistent with the A3
exclusion but matter for A2 with an unrestricted shell.
Audit rewriting and vault rollback. The unkeyed audit chain can be rewritten and rehashed by an attacker who
controls the whole file. The vault manifest MAC authenticates modifications under its key but does not prevent replay
of an older valid state. Detecting replacement, truncation,
or rollback requires an independently protected anchor and
monotonic revision state; same-user credential storage alone
does not establish that trust boundary.

RQ4: streaming equivalence. The current source contains TestStreamingMatchesBatch, a differential check over
3,000 deterministically generated inputs comprising registered patterns, fragments, gaps, and noise. It compares a
single write with chunks of 1–13 bytes followed by a final
flush. FuzzRedact additionally checks streaming/batch agreement and fragment coverage for its fixed pattern set. These
are executable regression specifications for Property 1; they
do not reconstruct the original historical run or constitute
exhaustive testing. The fresh paper/eval runs do not execute
these tests. The reproduction guide lists their commands and
platform-dependent checks.

fragment-indexed, and a structured secret’s boilerplate windows cause over-redaction (Table 3). Both trace to treating
every 12-byte window alike; weighting windows by estimated entropy, or decomposing URLs into their userinfo
component, are natural refinements. Separately, when two

Industry tools. Run wrappers inject secrets [2, 24, 41], and
op run also conceals them in output. Agent access products
broker credentials [1, 12]; Doppler’s MCP server deliberately
exposes values to agents [23] and Infisical’s can mask values
in its own responses [39]. Proxy substitution keeps values
out of processes for HTTP(S) [7, 26, 40, 58]; Secretless Broker
also supports database and SSH connectors [20]. The nearest
tools include fnox’s MCP server, with tool/secret allowlists
and exec that accepts agent-chosen argv, injects secrets, and
masks literal values [27]. Prismor’s Cloak substitutes placeholders before execution and filters literal output; its current
documentation also describes command policy and human
approval [61–63]. These documented controls overlap with
ironrun; we do not establish their historical availability or
equivalent enforcement semantics. Pattern-based scanners
and gateways inspect tool traffic [29, 64, 67, 71]. LangWatch
filters traces before storage or upload [45], and other tools
scrub existing agent histories [54]. Agent hosts now expose
hooks that can rewrite tool output [5] and ship their own
sandboxes [4, 7]. ironrun focuses on combining encoding-,
alignment-, whitespace-, and fragment-aware known-value
redaction with session-bound authorization and OS containment for arbitrary programs, and in evaluating that redaction
adversarially.

Related Work

Prompt injection and agent security. Indirect prompt
injection [33, 60] and its formalization and benchmarks [21,
48, 80] establish that an agent’s behavior can be steered by
data it reads, and adaptive attacks defeat most model-level
defenses [55]. Willison’s “lethal trifecta” [74] and Meta’s “rule
of two” [51] frame exfiltration as the conjunction of private
data, untrusted input, and an outbound channel. ironrun
reduces direct value exposure at the tool boundary and can
restrict network egress. It does not remove filesystem or local
IPC channels from the child.
System-level defenses. CaMeL [22], design patterns for
injection-resistant agents [11], information-flow control [18,
75], privilege policies [69], and execution isolation [76], building on the dual-LLM pattern [73], constrain what a compromised planner can do. ironrun is narrower and deterministic:
one data class (credentials), one sink (tool output), no change
to the model or planner. Its redactor is a fixed declassification
rule at a single boundary, and its strict mode corresponds to
the action-selector pattern at the shell level. A recent systematization of execution security for coding agents finds
deny-lists failing at high rates [66], consistent with our allowlist-first design.

Isolation and integrity primitives. Heavier isolation via
user-space kernels or microVMs [3, 79] and unprivileged
sandboxes [17] would strengthen containment at a cost. ironrun ships as one Go binary, using Linux namespaces/seccomp
or macOS Seatbelt; native secure-storage and platform sandbox tools remain host dependencies. Release signing follows
Sigstore [57].

MCP security. Measurement and attack studies of the
MCP ecosystem [15, 34–36, 81, 82] document tool poisoning [42, 72], credential theft through MCP-connected
tools [65], bidirectional data-flow risks [37], and context leaking into tool arguments of coding agents [78]. ironrun sits on
the return path of a local stdio server and assumes a possibly
poisoned agent.

10
Secret leakage and detection. Secrets leak widely in public code [50], code models can memorize them [38], and vendor data suggest AI-assisted commits leak more often than
average [28, 30]. Pattern-based detectors trade precision for
recall [9, 10]; ironrun sidesteps detection by matching only
values it injected. Closest in the literature, Kenney et al. evaluate a vault-mediated boundary for API connectors and conclude that output redaction is a separate, necessary layer [43],
and SlotGuard substitutes detected secrets at the transcript
boundary [77]. Chen et al. identify stdout-to-context as the
dominant leak path in agent skills without proposing a runtime fix [16].

Conclusion

Coding agents need to use credentials far more often than
they need to know them. ironrun filters known secret values and supported encodings from intercepted child-process
output. Its protection is limited by matching thresholds,
transformations, and the host-enforced execution boundary. A streaming known-value redactor with a provable
chunking property and session-bound human authorization with in-place continuation describe separate parts of
the boundary. The paired experiment measures redaction
coverage; platform controls provide additional, scoped restrictions. Regression case studies expose approval serial-
